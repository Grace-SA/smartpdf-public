# PDF→Word：Stirling 切换评估

初始评估日期：2026-11-13。初始结论：将 Stirling Office Convert 作为原生 PDF 的候选转换引擎，保留现有 OCR、公式与结构重建链路；不满足整体替换或直接上线条件。下文初始评估记录保留；用户批准后的实现及验收进展见末尾。生产部署尚未改变。

## 先区分两条转换路径

Stirling PDF 3.2.2 的 PDF→Word 接口通过 `useStirlingOfficeConvert` 区分新 Java Office 引擎和旧 LibreOffice `writer_pdf_import` 路径。不能把以前对旧路径的评估直接套到新引擎上。[固定版本控制器](https://github.com/Stirling-Tools/Stirling-PDF/blob/v3.2.2/app/core/src/main/java/stirling/software/SPDF/controller/api/converters/ConvertPDFToOffice.java)

- 旧 LibreOffice 路径：此前实际 HTTP 验证中，14 个支持范围内的合成样本返回 DOCX，但综合文档没有真实 Word 表格，依赖文本框，并出现裁切；不建议作为主要可编辑导出路径。
- 新 Stirling Office Convert：本次固定测试 3.2.2 核心包中的 `stirling-office-convert-0.2.2.jar`，能生成真实段落和 Word 表格。直接调用服务层使用的 `OfficeConvert.convert`，属于引擎验证，尚非 HTTP 服务部署验收。[服务代码](https://github.com/Stirling-Tools/Stirling-PDF/blob/v3.2.2/app/core/src/main/java/stirling/software/SPDF/service/OfficeConversionService.java)
- 新引擎本身没有完成扫描 OCR。本轮没有接入 Stirling 的 OCRmyPDF/Tesseract 前处理，因此不能用结果评价完整 Stirling+OCR 的识别准确率。官方也要求扫描件先 OCR。[转换说明](https://docs.stirlingpdf.com/Functionality/Convert/) · [OCR 说明](https://docs.stirlingpdf.com/Tools/Guides/OCR/)

独立 Office Convert 项目采用 MIT 许可；这不代表整个 Stirling 产品中每个模块均为 MIT。接入时应固定组件及传递依赖，保留相应版权与许可，页面署名按实际使用的组件展示。[Office Convert 项目及许可](https://github.com/Stirling-Tools/Stirling-Office-Convert/blob/main/LICENSE)

## 实测方法与范围

- 当前方案基线：`322aeac251ebcac397eaf4c07f48ef5a4f8aabbe`，完整 139 个输入。
- 新引擎：41 个定向样本，包括 18 个功能/边界用例及从主样本集抽取的 23 个文件；覆盖固定 12 份表格参考、3 份扫描文字参考及 20/23/98/196 页长文档。属于开发用定向样本，不是独立随机测试集。
- 核心 JAR SHA-256：`370a4218624fa4b3cf5460c886f03de01bfcfd2d4893009202a81e53b5f3344d`；Temurin 25.0.5+8；逐文件启动无界面 JVM，最大堆 768 MiB，处理器数量提示为 2。没有 GPU 依赖，也没有操作桌面 Word。
- 使用默认表格识别、`pictureFallback=false`、270 秒引擎时限；沿用现有输入预检。独立检查 ZIP CRC、XML、宏/嵌入对象、正文、表格及公式对象，并用 python-docx 编辑回存和重开。
- 8 份输出共 10 页通过独立无界面 LibreOffice 渲染，已逐页查看；复杂表格另与原 PDF 渲染对照。这是渲染检查，不能替代 Microsoft Word 验收。
- 所有输入、逐文件记录、输出、图片及可识别样本清单只保存在本地验收目录，未进入本仓库。

| 固定 12 份表格：严格单元格匹配 | 605/2762，21.90% | 1095/2762，39.65% |
| 同组表格：整份网格完全匹配 | 5/12 | 6/12 |

| 23/98 页两个长文档 | 各约 271 秒超时 | 约 1.94/5.17 秒生成并通过本轮结构检查 |

表格严格匹配增加 490 个单元格、17.74 个百分点；主要收益集中在两个表格参考上，不能外推为全部文档准确率。无框线、复杂旋转网格仍有明显失败。

41 个用例首轮记录：32 个含文字且通过本轮结构检查，5 个只有图片或无可编辑文字，3 个被既有输入策略预期拒绝，1 个生成后未通过包体限制。32 个不能称为整份文档可用：其中混合扫描件仅原生页面有可编辑文字。预期拒绝也不应作为转换器能力失败计算。全体 139 份的整体准确率仍未知，不能用 3 份文字或 12 份表格参考代替。

时长是本机定向引擎观察值，不包含 HTTP 排队、完整 OCR、下载与 Word 验收；当前方案长文档进入 OCR 的路径也不同。因此不能据此宣称等价质量下的端到端加速倍数或上线 SLA。

## 必须处理的限制

1. **扫描和低质量扫描没有被自动解决。** 5 个纯扫描输入没有可编辑文字；混合输入的扫描页仍为图片。重复标记只出现一次，简单“是否含某标记”检查会误判完整性。必须改为逐页覆盖、次数和内容检查。完整 Stirling OCR 前处理效果尚未实测。
2. **复杂表格仍有准确性及排版缺陷。** 有表格外观但没有 `w:tbl` 的输出；复杂双表输出第二张表超出页面右边界，原 PDF 并未越界。不能只按“生成了 Word 表格”验收。
3. **分栏与跨页延续存在回退。** 一页双栏文档的页脚落到新增第二页；跨页表格生成两张独立表，需要处理连续表结构和重复表头。
4. **公式能力未被替代。** 扫描公式用例的新输出没有文字或 OfficeMath；现有专用链路已有可编辑公式验收证据。尚未验证新引擎对原生行内公式的通用能力。
5. **不能直接接现有输出校验器。** 对 38 个实际生成包运行现有 `checkDocx`，全部被拒绝。基本输出的首个拒绝点是 ZIP 标志检查：Java 使用标准数据描述符位 `0x8`，现有检查只接受更窄的打包方式。这是接口兼容性，不能解释为 0% 内容准确率。需要严格支持数据描述符或经过验证的包规范化，保留 CRC、路径、关系、XML 和资源上限检查，不能直接关闭验证。
6. **196 页仍未验收通过。** 包生成且 CRC 正常，但有 1867 个 ZIP 条目、41,293,594 字节解压内容、12,539,767 字节主 XML；分别超过产品当前 1024 条目、32 MiB 总展开量和 8 MiB 单项限制。应优化输出与资源预算后复验，不能仅因文件存在宣布成功，也不能把首轮断言失败误报为引擎崩溃。

## 建议的接入范围

第一批：新增可开关的原生 PDF 引擎适配器，优先处理具有可靠文本层的正文、常规表格和长文档；修复 ZIP 接入兼容、表格宽度、分栏页脚与跨页延续；保留当前方案作为回退。识别模式与回退必须记录到逐文件结果，不能静默把整页图片算成可编辑成功。混合扫描、低质量扫描及公式继续使用现有 OCR/结构导出链路。

第二批：评估先 OCR 再进入新引擎的联合路径，重点补低质量扫描、无框线/合并单元格表格、行内公式；按实际页类型选择引擎，再组合文档。先验证阅读顺序、公式上下文、图片位置和跨页结构，不能简单拼接两个转换结果。

接入独立 Java 组件可以复用现有前端、队列、隐私处理、清理和限额，不必整体更换网站或购买云服务。需要新增 Java 25 运行环境及固定依赖的构建产物，并验证 Linux CPU 环境；原生引擎验证不必等待 GPU 配额。OCR 的 Linux GPU 验收是另一项尚未被本次测试覆盖的任务。

## 切换前验收门槛

- 冻结代码、依赖、139 份输入哈希与原有参考答案，对现有方案和候选路由完整逐文件比较，分别统计预期拒绝、超时、包校验、完整可编辑成功。
- 不允许已通过文件退化；分别报告文字字符准确率、表格严格单元格匹配、公式对象与内容、逐页覆盖及版式问题。当前 39.65% 表格严格匹配不满足“通用复杂表格可用”的承诺。
- 为低质量扫描、公式、复杂布局补独立参考答案与保留测试集，再谈扩大适用性；没有参考答案的文件不编造准确率。
- 对长文档验证全部页面和关键内容，并测峰值内存、超时、取消与清理。先修输出/资源控制，再有依据地调整限额。
- Microsoft Word 必须在不干扰用户的独立环境中完成打开、编辑回存、导出与实际版式对照。当前桌面 Word 自动化继续保持停用。
- 最后才进入受控发布、回退验证和既有发布流程。当前报告不构成全量切换或上线验收通过。

## 用户批准后的候选实现

新增可关闭的本地原生引擎适配器。`PDFWORD_LOCAL_V2=1` 仍是本地重建运行时的前提；再设置 `PDFWORD_NATIVE_ENGINE=stirling`、`PDFWORD_STIRLING_RUNTIME`、`PDFWORD_JAVA` 和 `PDFWORD_NODE` 才启用新路径。服务能力标记及页面底部的 Stirling Office Convert 署名随实际配置显示，原有三个 OCR 技术署名保留。默认生产镜像、版本固定值和共享模式限制没有改变。

离线准备步骤：用 Java 25 的 `javac` 执行 `python server/pdfword/stirling_build.py <已核对的核心JAR> <新的运行时目录> --javac <javac路径>`。构建器检查上文固定的核心包哈希，提取其依赖，编译无界面桥接器，记录每个运行时文件及桥接源文件的哈希。转换前重新核对这些哈希；组件 MIT 许可保存在 `vendor-licenses/stirling-office-convert-MIT.txt`。构建器不下载模型、依赖或用户文件；打包发布时仍须保留依赖 JAR 内的许可和通知。

原生入口逐页检查可见文本、扫描图片、透明/隐藏文字、缺字、裁切和公式特征。白字是否可见通过移除其渲染贡献前后的像素差验证，避免把白底白字或被遮挡的隐藏层当成可靠文本。已有明确网格、分栏、短跨页延续或需 OCR 的版面保留结构重建路径；这些选择是有意保留的回退，不宣称新引擎已经修复所有复杂布局。取消请求直接终止，不能触发重试。

完整重跑前的路由复核还发现，部分 PDF 的文字对象边界包含无实际字形的额外宽度，会把页面内文字误判成裁切。现在只在全部非空白字符能逐一映射回同一文字对象时，使用实际字形边界；映射不完整仍用保守边界。完全位于页面外的已映射字形从可见内容判断和原生裁剪提取中一起排除，真正部分裁切的文字仍走 OCR。合成测试覆盖映射缺失、真实裁切、页外文字不能进入输出、PDF 浮点页边差异；一个真实复杂表格的定向诊断在约 2.34 秒内完成原生重建，严格匹配 483/484 个单元格。该诊断不是全量最终指标，修复后的源码重新冻结并重跑完整验收。

Java 输出先经过独立规范化：验证 ZIP CRC、XML、关系及资源限额，拒绝外部关系，统一图片并去除相同像素的重复媒体，转换标准 Java 数据描述符包，按实际可用页宽同步调整表格网格与单元格宽度。最终仍通过原有 Node DOCX 校验器，没有放宽产品的 1024 条目、32 MiB 展开量、8 MiB 单项及 30 MiB 下载限制。逐页文字覆盖和数字保留检查不通过时回退；这类内容保留检查不是独立参考答案准确率。

结构导出器另修复两类已复现问题：同一行的并列图片按原位置放在同一段落，避免上下堆叠；具有明确延续标题、相同几何且无其他正文的跨页表格可合并，不再要求该局部标题在整份长文档中大量重复。一般分栏仍使用已有的 Word 分栏重建器。

逐文件对照随后发现了包校验无法揭示的两类遗漏，已加入保护：新引擎若在有已知图形的源页输出零张正文图片，则回退；原生重建若把大段可见文字合入背景图片，则交给现有 OCR。保留图形中的短标签可以继续作为图片内容，不能宣称这些标签已可编辑。矢量图形的窄笔画和细线也予以保留，避免字形被尺寸过滤器截掉。这些检查用于发现明显遗漏，不替代源 PDF 与 Word 渲染的逐页核对。

对“表头有列线、正文缺少内部线”的数值表格，使用已有表头列位置和重复对齐的数值行补建正文网格，保留部分缺值为空单元格；仅由空白相邻列产生的虚假行边界被合并。合成测试覆盖缺线、部分缺值和空白列的局部线段。一个补充开发用例已按源页手动核对 33 行、66 个数值，全部位于对应列，两个无数据年份列保持为空；实际 Word 编辑回存及一页导出均通过。这份补充诊断不加入固定 12 份表格的原有分母，也不是新的独立保留测试集。

实际 Word 对照进一步发现，新引擎可能把嵌套网格展开成普通文字，却仍通过文字和包结构检查。现在检测到内外嵌套网格时保留原有结构/OCR 路径；如果回退也无法可靠重建，则明确拒绝，而不是把不正确的表格算作成功。这是路由保护，不代表已经实现通用嵌套表格。

另一类 PDF 用白色矩形作为正文背景，旧提取会把整段文字并入图形，触发不必要的 OCR，定向 Word 对照中出现过重复列表。现仅对无旋转、坐标明确的根级白色矩形做保守处理：检查绘制顺序和先前对象的重叠，再临时隐藏候选矩形，比较有界高分辨率 RGB 渲染；只有完全无像素变化才从版面分析中排除，并始终恢复原绘制状态。覆盖已有内容、彩色图形、变换不明确或检查不通过的矩形仍保留。测试覆盖亚像素隐藏文字、相邻背景的坐标舍入、实际遮挡及渲染失败后的恢复。一个补充 13 页文档已无需 OCR 完成转换，实际 Word 中 14 项列表均可编辑且只出现一次；装饰下划线仍可能单独重排，不能声称像素级版式一致。

OCR 还可能同时返回完整多行区域及其内部的重复文字区域。现在只有在区域被包含、标准化后的完整行内容一致且纵向位置匹配时，才去除重复子区域；不同位置的重复短语、不同数值、部分行、表格和公式对象均不会按同样规则删除。分栏重建在等分页面不能解释版面时，再尝试从明确的文字间隙推断栏界，并继续拒绝与跨栏内容重叠的模糊布局。一份补充三栏文档已重新从原图识别并通过实际 Word 验收，保留三栏阅读顺序，七条侧栏链接各出现一次；标题位置、背景色和字体比例仍不完全相同。这些修复触发了新的源码冻结及全量重跑，之前的部分结果不拼入最终批次。

## OCR 组合验证与验收状态

三个开发用定向样本使用同一 OCR 结果比较现有结构导出和“原图加隐藏 OCR 文本层，再送入 Java 引擎”。该试验不等同于 Stirling OCRmyPDF/Tesseract 服务验收，也不具备独立 OCR 准确率参考。正文样本没有显示内容收益；表格的两张网格由 3×10、5×9 变成 5×10、8×9，不能保持已有单元格归属；公式样本由 23 个 Office Math 对象变为零个，公式文字仍可能存在，不能把对象丢失称为全部文字识别失败。因此扫描、混合和公式继续使用现有 OCR 结构输出，组合路径未进入默认路由。

用户随后明确允许在本机运行 Word，替代此前独立环境要求；旧批次仍保持暂停。当前冻结候选的 15 个功能输出均通过 Microsoft Word 16.115 打开、编辑回存、重开和 PDF 导出，以及正文/页边文字、图片、单元格与合并关系、源页标记和公式保留检查。其 27 页未编辑 Word 导出已逐页查看，六张表格没有超出页宽；23 个可编辑公式仍保留。跨页表合并后可减少 Word 页数，不能要求与源 PDF 页数机械相同。

同一候选的 139 份全量重跑、固定参考准确率和全量实际 Word 验收仍在进行。首批 15 份通过不能替代全量成功率，也不能把旧版 96/139 或直接引擎的 1095/2762 写成当前混合路由的实测结果。所有逐文件证据、输入、渲染和模型继续只保存在本地。
