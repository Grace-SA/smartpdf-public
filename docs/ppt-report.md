# PowerPoint 转 PDF：本地开发与验证

日期：2026-11-05。分支：`feature/ppt-to-pdf`，基于 `main` 的 `de579d7` 独立开发。状态 **Testing，非 Accepted，未合并、未部署**。用户已授权在前期调研基础上继续开发。本次未改动其他工作目录的 Excel 工作。

## 产品与实现

入口 `/powerpoint-to-pdf/`，与现有 Word 共用工具目录、导航、视觉样式、文件选择器、PDF 预览和任务生命周期。单个标准 PPTX，30 MiB 输入/输出，最多 250 张源幻灯片、200 张可见幻灯片。选择与本地基础检查不上传；用户点击 `Upload and convert` 才创建任务并上传。选择时生成不可变字节快照，检查和上传使用同一份内容。

保留原尺寸/比例和可见页顺序，每张可见幻灯片输出一页。隐藏页、备注页和批注不输出；动画静态化。结果突出下载，预览按需打开，转换下一份前删除临时结果。初次设计自查后又根据实际手机布局移除结果页重复的上传说明，避免主下载动作被大量文案挤到下面。最终布局仍需产品负责人和真实手机验收。

支持文本、普通主题/母版、形状、表格、内嵌 PNG/JPEG、常见标准图表及其内嵌 XLSX 数据。老 `.ppt`、其他 Office/ODF 格式、宏、密码、签名、嵌入媒体/字体、ActiveX/OLE、远程资源不自动开放。SmartArt、公式、SVG/EMF 等复杂特性尚无充分质量证据，不宣传完全保真；遇到未知资源会给出具体不支持提示，而不是把已有普通图表一律拒绝。

## 固定开源环境与适配决策

配置为 `config/ppt-core.stirling-3.2.2.json`；PPT 专用镜像身份：

`sha256:3c274ecae5cb89ebeaeaf85d9d715f9c69df32b352934ae70a7dd7245a75e9be`。

基于已有开源核心候选 `a6bdc6c64f0f0287043f073cca79bcafd515cc9c5a6786c76a6c4deb2af9e6ee`，保留 LibreOffice 26.2.6.3 与字体，补齐校验锁定的官方 Colibre 图形资源，允许普通内嵌图表但继续阻止宏/OLE 自动执行。构建文件为 `server/ppt/Dockerfile`，`doctor.py` 在构建前后核对身份；重建不会自动修改运行 pin。初轮复用了本机 Excel 候选作 PoC，随后建立独立 PPT 镜像并重跑原样本，不将初轮成绩冒充最终镜像成绩。

**实际转换由该核心容器内的 LibreOffice Impress UNO 完成，未启动 Stirling Java HTTP 包装器。** 这是为明确控制隐藏页、备注、原稿嵌入和演示输出选择的适配；并不宣称现有 Stirling REST 已验证支持全部参数。显式使用 `NEVER_EXECUTE`、`NO_UPDATE` 和 `impress_pdf_Export`。不引入付费转换服务、不调用 Microsoft/Adobe 云接口，也没有更换 Word 或 Excel 的镜像 pin。

每任务非 root、只读容器，`network=none`，无宿主文件挂载和公开端口，2 CPU/2560 MiB/512 PID，RAM 临时目录 512 MiB，总任务预算 120 秒，Office 命令预算 90 秒。源包在进入引擎前有 ZIP/CRC/路径/XML/关系、嵌套图表数据与图片像素预算；Windows 上检查 `orig_filename`，防止库的路径规范化掩盖反斜杠/空字节。

任务服务复用 Word 的同源会话、队列、流式容量限制、过期、取消和清理逻辑；PPT 使用独立 API 路径及 Cookie，拒绝 Word 输出选项。输出先用 Poppler 核对页数与尺寸，再在独立 Node Worker 用 pdf-lib 检查全部页面、附件、批注和活动操作。HTTP 成功不直接作为可下载条件。

**部署边界：** 当前为独立本机 PPT 服务，复用的是任务实现，并非已完成跨 Word/PPT/Excel 进程的全局容量调度。在现有小规格生产主机启用前，必须验证共同资源预算、公平队列、反向代理、HTTPS、目标镜像与清理策略。当前本地工作不授权扩大生产容量或发布。

## 本地运行

先核对 `doctor.py` 所需的基线镜像与 PPT 镜像；若需重建，先验证基线 tag 与配置的 `baselineImageId` 一致，再使用空构建上下文构建 `server/ppt/Dockerfile`，审阅新镜像身份，不自动提升。

后端：`node server/ppt/service.mjs`，默认只监听 `127.0.0.1:4281`。配置 `PPT_PUBLIC_ORIGIN=http://127.0.0.1:4280`。当前共享服务的处理地区与本机标识使用 `WORD_PROCESSING_LABEL` 和 `WORD_PROCESSING_MODE=local`；Windows 可配置 `WORD_WSL` 指向现有 WSL。PPT 存储目录由 `PPT_DATA_DIR` 单独指定，禁止备份。

前端：正常构建后在 `127.0.0.1:4280` 预览，Vite 将 `/api/ppt` 转发到本机 4281。只用于本机验收，不宣称其他设备已经可访问。系统内存紧张时采用单构建线程与逐项测试，不同时运行全部浏览器和 Office 转换。

## 证据与失败记录

全部原始日志、合成源、PDF 和截图保存在忽略的 `.research/ppt/`，未加入 Git。未使用私人演示文稿。

- 24 个固定合成 PPTX，覆盖 16:9、4:3、自定义、竖版、中文、换行、普通/合并表格、七类常见图表、PNG/JPEG/透明图、旋转形状、主题/母版、隐藏页、备注、链接和有意空白页。
- 初轮候选：24 份/27 页完成独立文字、页数、全部页尺寸、附件/注释检查及 PyMuPDF 逐页渲染目视；图表和图片另查图形/图像资源。绘图数通用诊断阈值曾误判饼图，改为类别语义后重新验证；不是转换器缺失图表。
- 独立 PPT 镜像并发负载轮：24 份中 2 次转换失败，保留原记录，未计作首次全通过。随后停止大规模并发，使用同一输入哈希与最终代码完整复测，24 份全部转换成功，独立核对 27 页通过。旧输出先移走，复测先删除输出，验证器要求转换状态全部成功，防止读到前轮 PDF。压力下失败原因未充分定位，不作为吞吐/SLA 认证。
- 真实 Chromium/WebKit 手机宽度流程已验证上传、转换、下载、PDF 预览、删除；此项不是物理手机验收，也不能代替最终提交 CI。
- 真实转换中取消：检查运行中容器的断网、只读、用户身份、零宿主绑定挂载/公开端口；取消至清理确认 1313 ms，结果不可读取。第一次实验在 `starting` 就检查容器，早于创建；修正为等 `converting` 后重测，保留观测失败。
- 一轮完整单元与集成回归 573 项通过；其后少量代码修正的最终回归另记录，不能用这一轮替代新代码的检查。
- 首轮本地累计浏览器尝试被中断，已发现 PPT 缺少统一相关工具区并修正；另有原浏览器截图失败。专项测试曾有 WebKit 对 File-backed XHR 不提供截获正文、默认 5 秒等待低于项目原有 30 秒基线等差异；截获支持时仍核对字节，所有平台核对媒体类型，真实字节/输出另由实际服务验证。
- 文件选择器同步重置曾导致合成输入偶发不可读，已改为先保存不可变快照，检查完成后再重置原生选择器；需以最终浏览器结果为准。
- 本机可用内存曾仅约 15 MiB，出现原生构建内存分配失败；停止本轮并发、关闭调研标签页并限制构建线程后构建成功。没有停止其他项目进程；失败记录不删除。

## 竞品回看与剩余门槛

iLovePDF 已实际观察选择、文件卡片、明确转换和处理中状态；精简合成输入被提示“需要密码”，标准结构输入重新观察未取得可独立核对的下载。Smallpdf 已查看真实入口，文件选择器事件超时，未完成上传任务。这两项不能写成完整竞品闭环通过。产品采用简短流程与明确上传，但不据此宣称效果胜过竞品。

尚需：补齐至少两个竞品的完整正常/错误/取消/重做与窄屏任务；Microsoft PowerPoint 原生参考 PDF 对照；动画构建、复杂 SmartArt/公式/矢量素材与字体的扩大验证；目标主机共同容量调度；精确提交 CI 和真实手机/产品负责人验收。输出可搜索和自制样本正确不等于完整 PPT 兼容认证。

后续提交须先运行仓库检查，经现有 origin 同步本地 bare/GitHub/Codeup，并逐端核对分支对象。任何未完成门槛保持 Testing，不自动合并或上线。
