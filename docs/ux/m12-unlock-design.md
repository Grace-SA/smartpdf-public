# M12 Unlock PDF — 产品与技术方案

2026-10-28：用户已确认 M12 真机测试通过，当前状态 **Accepted**。最终 UX 复核保留选择文件 → 必要时输入密码 → 解锁 → 下载的独立任务边界，不增加阅读器或跨任务编辑。用户授权在代码复核、累计回归和精确主分支 CI 通过后发布，并同步 GitHub/Codeup；以下方案阶段的授权与待测描述作为历史记录保留。

日期：2026-10-23。方案基线已完成，当前进入 **Testing**。方案阶段曾按用户要求停在产品编码前；后续调用方确认传递 `thinking=high` 并省略 `model`，本任务无法独立读取实际模型/档位，不记录推断值。浏览器技术门槛已先验证后实施产品，进展见 [M12 研发记录](../m12-report.md)。原方案及分阶段要求保留如下，不把未完成的真机验证写成通过。此要求不影响其他任务。

本轮没有生产发布、付费、私人文件上传或其他工具加密输入扩展授权。既定 M12 是解除已获授权文档的密码保护，不是密码找回服务。

## 1. 基线与研究证据

本机与远端 main 核对一致，研究基线为 `6c24dee`。当前仓库没有 M11 产品实现或密码适配层，requirements 中 M11 仍为 Not started。因此下文复用的是已经锁定的 M6 qpdf WASM 和通用任务机制，不能把 M11 的功能或验收当作已有证据。分支为 `feature/m12-unlock-pdf`；未修改产品运行代码。

研究包括三个竞品的实际入口检查、官方功能/帮助文档，以及锁定依赖的本地合成探针。没有向竞品上传任何文件；密码页、错误页和完成页的竞品细节若未实际触达，不写成已实测。也不从网站文案推断其内部算法。

| 竞品及来源                                                                                               | 已核对的做法                                                     | 采用的体验原则                           | 不照搬的部分                                               |
| -------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------- | ---------------------------------------- | ---------------------------------------------------------- |
| [iLovePDF](https://www.ilovepdf.com/unlock_pdf)、[官方帮助](https://www.ilovepdf.com/help/documentation) | 入口突出选择文件和解锁动作，支持云盘入口                         | 一个明确主动作，选择文件后保持任务简单   | 不增加云盘、上传进度或含糊的无密码解锁承诺                 |
| [Smallpdf](https://smallpdf.com/unlock-pdf)                                                              | 官方说明为选择、输入密码、下载；支持后续编辑，网页处理涉及服务器 | 需要时才问密码；结果直接下载             | 不加入跨任务连续编辑、分享或账号分流；不声称知道其内部实现 |
| [PDF24](https://tools.pdf24.org/en/unlock-pdf)                                                           | 明确要求已知密码，并区分在线服务与本地桌面产品                   | 清楚解释未知打开密码无法恢复，保留原文件 | 不复制广告、重复说明、云端文件保留策略                     |

共同基线：选择 → 必要的访问凭据 → 一次处理 → 下载。我们的差异是文档和密码均留在浏览器，密码错误可原位重试，完成后任务结束。无需页面整理器、缩略图网格、完整阅读器或全局文档历史。

## 2. 场景与功能边界

目标场景：用户知道银行账单、合同或个人归档 PDF 的有效密码，希望得到不再询问打开密码的副本；或者文档可直接打开，但存在打印/复制等权限标志，用户获授权移除保护。

- 一次一份 PDF；输入和输出各不超过 30 MiB、最多 200 页；输入加候选输出总量不超过 60 MiB，沿用对象、深度、流解码及时间预算。
- 有效 user 或 owner 密码均可尝试；空打开密码仅在实际验证可访问后走无需输入密码的路径。
- 目标覆盖 Standard Security Handler 的常见 RC4-40、RC4-128、AES-128、AES-256 历史输入；实际支持矩阵由浏览器技术验证确定，不能仅凭算法名称承诺兼容。
- 未加密输入明确说明无需解锁，不复制一份文件并算成成功。未知密码不猜测、不枚举、不做暴力尝试。
- 证书型安全处理器、不支持的 crypt filter、损坏或超预算输入明确拒绝。
- 保留页面、文字、图片和可支持的链接、书签、标签、图层、表单等结构；无法验证安全保留时拒绝，不用打印为 PDF 或整页图片作为降级。
- 已有数字签名、认证签名、DocMDP 或 C2PA 不以解锁为由静默失效；首版明确拒绝这类输入，原件不变。不能把可见手写签名图片误判为数字签名。
- 标准符合性声明在解密后经现有检查识别；若需要生成普通副本，沿用显式确认原则。未确认不移除声明，也不宣称重新认证标准。
- 不修改 Merge、Split、Sign 等工具对加密输入的准入规则；它们仅可由用户另起任务选取已下载的普通副本。

## 3. 完整任务交互

### 3.1 选择文件

路由 `/unlock-pdf/`，标题 `Unlock PDF`，一句副标题 `Remove a known password. Keep your PDF on your device.`。

上传模块唯一主按钮 `Select PDF file`，支持拖放；保留原生 input/label 激活，不等待异步引擎才启用选择。支持说明、FAQ、其他工具放在操作区下方；选中后全部收起，仅保留现有 `Private by design` 行。引擎按需静默加载，初始化不得撑开布局或挤走按钮。

文件尺寸/类型先检查，再进入独立解锁检测。检测只提示简短的真实状态，超过既有阈值才显示工作反馈；没有 `Tools are getting ready` 一类技术文案。

### 3.2 文件选定后的状态

桌面为居中的单卡片，手机为同一张单列卡片。顶部只显示文件图标、可换行名称、大小，以及 `Choose another file` 文本按钮。无需解密前的页面缩略图。

| 状态                 | 页面内容及动作                                                                                                                   | 下一步                                                |
| -------------------- | -------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------- |
| 需要密码             | `Enter the PDF password`；一项带明确 label 的密码框，默认隐藏；旁边 `Show password`，切换时不提交也不丢焦点；主按钮 `Unlock PDF` | Enter 或主按钮提交一次，阻止重复提交                  |
| 错误密码             | 输入框下方 `That password didn't open this PDF. Try again.`，以 aria-live 通知；保留文件，允许继续编辑                           | 只在下一次显式提交尝试，输入时不自动探测；不回上传页  |
| 可直接打开的加密文档 | `This PDF opens without a password. Remove its remaining protection.`；不显示无用密码框；主按钮 `Unlock PDF`                     | 一次明确操作后创建副本；不偷偷转换                    |
| 未加密               | `This PDF isn't password-protected. No unlocking is needed.`                                                                     | 只有 `Choose another file`；不显示成功图标或 Download |
| 不支持的安全处理器   | `This PDF uses a protection method we don't support.`                                                                            | `Choose another file`；不反复要求密码                 |
| 损坏/过大/复杂度超限 | 对应稳定原因，说明原件不变                                                                                                       | 换文件；不展示原始解析异常或文档片段                  |

密码区只补一句 `Use PDFs you own or have permission to unlock.`，不加入第二个密码确认框、强度仪、算法选项或营销区。

密码不得 trim、大小写转换或静默截断。正确处理前后空格、引号、等号、中文和 emoji；对不能准确传递的控制字符或编码明确说明，不悄悄改写。Show/Hide 是具备可访问名称的普通按钮，不用不可识别的图标孤立表达。

### 3.3 处理中、失败和取消

开始后禁用提交和换文件，显示单一取消入口，保留清楚的工作反馈。只给出真实阶段：解锁、检查输出、准备下载；不伪造百分比。

取消立即终止该次 Worker 和候选，不返回成功。超时、Worker 崩溃、WASM 加载失败可原位重试；失败后重建 Worker。不能让旧请求的迟到回复写入新任务。

错误密码允许保留当前输入供用户纠正，但不得在多任务缓存中保留；完成、取消、换文件、离开任务和组件卸载均清空输入与引用。离开已选文件任务沿用统一二选一对话框：`Keep editing` / `Discard task and leave`，不加入 Apply。

### 3.4 完成与后续动作

整页切换到完成态并滚到页面顶部，卸载密码表单和操作栏。标题 `Your unlocked PDF is ready`；文件名默认为原名加 `-unlocked.pdf`，正确处理已有扩展名和长名称。

唯一强主动作 `Download PDF`；弱动作 `Choose new files`，提示先下载再开始新任务。保持既有本地处理说明，不恢复编辑器、不展示 Document history、跨任务 Undo/Redo 或自动接着处理。

从完成页点 Choose new files，或 Tools → 任意其他工具，都必须得到空的新任务，第一次点选择文件即能调起系统选择器。解锁结果不自动注入其他工具。

手机不引入横向密码面板；输入字号至少 16px，触控按钮至少 44px，软键盘打开时输入和动作可见；短横屏不固定覆盖内容的底栏。页面不得横向溢出。

## 4. 技术选型与已做验证

选择现有 `@neslinesli93/qpdf-wasm@0.3.0`，实际引擎报告 **qpdf 12.2.0**，不升级依赖、不引入远程 API。以独立按需 Worker 执行结构重写的 `--decrypt`，不调用图片压缩或页面复制接口。

候选比较：PDF.js 可用于重新打开/渲染验证，但不是保留文档结构的解密写出器；pdf-lib 的 `ignoreEncryption` 不能充当解密；服务端工具不满足本项目本地处理原则。不为当前功能引入新服务或替换全站核心。

官方能力依据：[qpdf 命令](https://qpdf.readthedocs.io/en/stable/cli.html)、[加密说明](https://qpdf.readthedocs.io/en/stable/encryption.html)、[WASM 项目](https://github.com/neslinesli93/qpdf-wasm)、[构建入口](https://github.com/neslinesli93/qpdf-wasm/blob/master/build.sh)。这些是候选能力依据，不能替代锁定构建实测。

本地隔离探针（仅合成文件；未提交二进制）验证：

- RC4-40/128、AES-128/256 分别使用有效 user/owner 密码；另有 Unicode AES-256 和空 user 密码路径。共 11 份解锁输出，经独立 PyMuPDF 验证 22 页，无加密、文本/几何/像素与明文来源一致。
- **发现的返回码差异必须适配**：锁定构建对无/错误密码的 `--requires-password`，以及未知密码时的 `--is-encrypted`，实际返回 2 并报告 invalid password；有效密码返回 3。不能把 2 一律解释为未加密。全新实例复验也出现此行为。
- `print` / `printErr` 不在该构建的接收参数中，不能用它们阻止诊断输出。已验证的办法是 `noFSInit: true` 加 `preRun` 中的 `FS.init` 字节回调，隔离 stdout/stderr。产品只能暴露稳定错误类别，原始诊断不得发回主线程、日志或埋点。
- 技术探针正常路径已检查虚拟 PDF 文件清理。产品仍应每次操作结束 terminate Worker，避免 qpdf 调用栈、参数和密码继续驻留。

本机证据在忽略目录 `.research/m12/`：`qpdf-probe.json`、`status-probe.json`、`independent-probe.json`。首轮输出拦截失败记录不改写为成功；后续通过 FS 回调解决。上述是 Node 可行性结果，**不是浏览器、真机或全部结构支持已通过**。

## 5. 实现架构与安全边界

1. 独立 `unlock` 模块：纯状态/错误模型、限额与加密字典识别、Worker 适配、服务生命周期、简单工具面板。已有压缩 Worker 不接收密码，不为研究预建整个 M11/M12 平台。
2. 先校验头尾、尺寸和结构预算。在隔离 Worker 中仅检查加密字典及必要目录；若使用 pdf-lib 的 ignoreEncryption，仅用于加密元数据识别，禁止将未解密内容交给编辑或输出代码。缺失引用、重复字典和异常安全处理器不能判为普通未加密文件。
3. 不仅依赖有缺陷的状态码。结合已验证的加密字典、有效访问和命令结果分类：未加密、需密码、密码错误、无需打开密码、算法不支持、损坏、预算不足。不要以捕获全部异常后都提示 Wrong password 兜底。
4. 原始密码只留在组件及当前 Worker；通过内存参数传递，不拼接 shell 命令，不进入 URL、虚拟文件名、持久存储、Service Worker 缓存或外部请求。若采用虚拟密码文件，必须先解决逐行读取会截断换行的问题；初版优先使用精确内存参数并限制不能精确表达的输入。
5. Worker 内通用路径如 `/input.pdf`、`/output.pdf`；从不使用个人文件名做诊断路径。输出回调只在任务内分类并限制容量，随后丢弃；不使用可能披露 user password 的 `--show-encryption`。
6. 输入先验证可访问，再结构重写。候选必须无 Encrypt，能以空密码重新打开，通过普通结构/内容验证及页数、页面几何、目录结构比较。仅 PDF.js 能渲染或 qpdf code=0 都不构成完整成功。
7. 保真检查覆盖可达对象及逻辑结构，不要求对象编号/压缩字节一致。用有界规范化对象/流检查辨识内容和导航、表单、标签、图层等变化，忽略仅加密状态、xref 和合法对象重编号差异；无法可靠比较的结构不得静默丢弃。开发中先用复杂合成样本验证此策略，不以一张普通页面探针替代。
8. 校验后才创建下载 URL。失败/取消清理虚拟输入、输出及密码文件，撤销候选 Blob URL，terminate Worker，释放数组与密码引用。不能承诺 JavaScript 能证明擦除所有内存副本。
9. 聚合统计只增加 `unlock` 工具枚举及固定结果类别；密码、原始异常、文档内容、文件名、路径、解密字典或诊断全文不得上报。不因密码错误次数扩展用户跟踪。任何统计失败都不能阻止生成或下载。

## 6. 开发前技术门槛

方案阶段曾按用户要求暂停，下列项目在后续开发轮次继续验证；当前浏览器/结构门槛及实现结果见研发记录，真机上限仍待实测。未通过的项目不能写成已经支持：

- Chromium/WebKit 的真实 Worker 验证：上述算法/角色、Unicode、空密码和错误后重试、诊断不外泄、取消/超时/销毁；不只测试 Node。
- 旧 R5、混合密码编码、带权限空打开密码，以及 certificate/custom security handler 的明确识别；独立解析器交叉验证。
- 结构丰富输入：链接、书签、PageLabels、可编辑表单、标签、图层、附件、元数据；识别数字签名和 C2PA，不能在生成后才意外降级。
- 200 页、大图、异常页面尺寸、30 MiB 内存预算；50 MiB、100 MB 在读入引擎前安全拒绝。内存/取消行为需要 iPhone 技术验证后才确认手机支持上限。

如锁定构建无法满足以上门槛，先报告具体失败、候选方案及影响，不自行升级引擎、改为上传、降低保真标准或扩大加密支持承诺。

## 8. 方案二次对照后的减法与结论

已将最初可选的阅读器预览、权限矩阵、密码确认输入、完成后继续编辑去掉；这些都不是一次解锁任务的必要步骤。保留竞品最短任务路径，同时补齐本地处理、可恢复错误、未加密不伪成功及明确完成边界。

产品方案与技术路线基线先形成，再按用户阶段设置进入开发。实现后仍按第 6、7 节验证，不以局部技术探针替代全站回归或真机验收；当前没有发布上线或产品验收通过的结论。
