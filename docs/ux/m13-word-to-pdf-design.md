# M13 Word 转 PDF：产品、交互与技术方案

研究日期：2026-10-26—27。状态：**Design，技术验证尚未通过**。
对应用户指令：先竞品体验与交互，再 GitHub 技术研究，确定方案后开发和测试。
这是可审阅的产品方案和已执行的研究原型，不是功能验收或上线许可。
完整实测结果见 [研究报告](../m13-report.md)。

## 1. 决策

保留浏览器本地处理、不要求手动打印、覆盖手机的既有产品目标。主选研究方向是
完整 LibreOffice WASM 排版引擎，不选 Mammoth/HTML 截图作为保真转换主线。
`@matbee/libreoffice-converter` 2.7.2 目前只作为实验候选，**不加入生产依赖**。

当前不能冻结生产引擎：桌面 WebKit 对含图/页眉页脚的诊断输入超时；当前二进制
最低导入内存为 1 GiB；退出路径失败。先解决这些问题再进入产品实现。
不能把桌面 Chromium 的成功写成 Safari/iPhone 支持，也不能自动改成云端转换。

## 3. 我方任务流程

`选择 DOCX → 本地检查 → 必要的兼容性确认 → 转换 → 下载 PDF`。
不引入文档编辑器，不要求用户配置 DPI/纸张或通过浏览器打印。

| 状态 | 呈现与主动作                                                                              | 恢复规则                                                     |
| ---- | ----------------------------------------------------------------------------------------- | ------------------------------------------------------------ |
| 选择 | 标题 `Word to PDF`；主按钮 `Select Word file`；说明仅 `.docx`、30 MiB、留在本机；支持拖放 | 无需等待引擎初始化才能打开原生选择器；取消选择不改变状态     |
| 检查 | 在固定高度区域提示 `Checking your document…`；本地读取与有界解压                          | 失败说明原因，保留可替换文件入口，不产生输出                 |
| 就绪 | 文件名、大小；主按钮 `Convert to PDF`；次要 `Change file`                                 | 不增加空预览步骤；仅缺字/字体替换等确有用户选择时显示说明    |
| 转换 | `Converting…` 与 `Cancel`；首次大资源下载须显示真实字节进度和大小，下载资源不是上传文档   | 不伪造每秒递增百分比；取消立即终止隔离上下文，旧响应失效     |
| 完成 | 以 `Download PDF` 为唯一主动作，次要 `Convert another Word file`；可选查看生成 PDF        | 重复下载同一字节；下一份任务完全重新选文件，无跨任务文件沿用 |
| 错误 | 可操作的简短原因：格式不支持、损坏、受保护、资源不足、转换超时                            | 更换文件或原位重试；无云端自动回退；原件始终保留             |

大引擎说明不可隐藏：是否接受一次 80+ MiB 下载是待验证的产品问题，不应让用户
先选择文档再无反馈地等待。工程资源准备不抢占主动作、不导致布局跳动。
该候选成本远高于现有工具；在实测达标前不添加路由、首页入口、SEO 或可用性宣传。

无障碍与手机：原生 input/label 激活；拖放有同等按钮替代；状态使用 `aria-live`；
按钮可触摸且支持键盘；焦点在错误/完成时有确定去向；取消不弹无价值确认框。
前进后退、工具切换和下一任务必须取消当前代次，不展示上次文件或结果。

## 4. 拟定支持矩阵（尚非已支持声明）

| 输入特征                                                                   | 首版目标行为                                                                                       |
| -------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| 单份普通 DOCX，段落、编号、表格、图片、显式/自动分页、页眉页脚、横竖版分节 | 必须覆盖，不能为绕过当前失败移除这些核心类别                                                       |
| 中英文字体                                                                 | 已有 OFL Noto Sans SC 可作为受控字体来源；替代字体会改变换行，检查后明确提示，不承诺 Word 像素一致 |
| 日文                                                                       | 一小段样本能显示不等于完整覆盖；扩充日文字体及字符集验证后确定支持范围                             |
| 旧 `.doc`、`.docm`、伪装成 DOCX 的宏包、嵌入对象                           | 首版拟拒绝；不以底层引擎声称支持全部 Office 格式                                                   |
| 加密 Office 容器、数字签名、修订、复杂域/外部模板                          | 检出后明确拒绝或待方案；不能静默去除签名、接受修订或刷新外部内容                                   |
| 普通外部超链接                                                             | 不访问目标；PDF 链接仅允许审阅后的安全协议；外链图片/模板/INCLUDETEXT/DDE 等主动内容拒绝           |
| 损坏 ZIP、CRC 不符、重复/穿越路径、异常解压、空内容、超预算                | 在进入 Office 引擎前安全拒绝，不只依赖扩展名                                                       |
| 输出                                                                       | 可选择/搜索的矢量文字 PDF，图片保留；不做整页截图降级；不自动嵌入原 DOCX                           |

拟定外层契约：输入 ≤30 MiB、输出 ≤30 MiB、输出 ≤200 页；处理前限制 ZIP 条目
数与累计解压字节，处理后独立解析页数/尺寸/结构。精确解压预算和极限页数超时
须以冻结边界样本实测确定，不能仅检查 ZIP 元数据后无界解压。

## 5. 技术架构与安全边界

1. **输入预检**：独立 Office 模块；解析包清单、关系和内容类型；有界解压、验证
   元数据/CRC/路径一致性；禁止宏、主动域、远程图片与自动外部资源读取。
2. **资源加载**：固定版本、校验哈希、同源字体与 WASM；延迟到当前任务加载。
   COOP/COEP 仅在隔离转换页面/子上下文验证，不贸然修改全站下载与导航行为。
3. **排版执行**：一个任务一个可销毁隔离上下文；采用 Worker 以保持主界面响应；
   不依赖上游等待消息的 `destroy()` 作为唯一取消机制。需要验证子线程一并释放。
4. **任务状态**：所有消息绑定任务代次；新选择、取消、超时和离开使旧代次失效；
   超时须真正终止工作，不只是 `Promise.race` 后忽略仍在运行的引擎。
5. **候选输出复核**：独立 PDF 解析验证大小、页数、几何与有效结构，再转交现有
   完成页/下载机制；测试另用 Poppler/pypdf 核对文字、图片和渲染。
6. **隐私**：禁用引擎文档/路径日志外发，CSP 与请求拦截作为纵深控制；不能把本轮
   六份离线合成测试无外网请求当成恶意 DOCX 已全面防护的证明。

复用现有任务、取消语义、下载命名与完成页；不把 Word 解析塞进 PDF Core。
研究原型特意没有这些完整防线，只允许合成 fixture，不是面向用户文档的转换器。

## 8. 后续开发顺序

先做引擎攻关：定位 WebKit 含图/页眉页脚导入卡顿；修复退出路径；重编译并缩减
Office模块、字体与最低内存，核验许可与可重现构建。保留原始失败和样本身份。
复跑固定六类，再扩充修订/脚注/浮动对象/多栏/大文档/恶意包样本，并测真实 iPhone。

只有技术门槛通过后才实现预检、任务适配和正式交互，再执行 unit/integration、
所有边界、全量累计回归、独立PDF核对、竞品复查与真机验收。不得提前宣传可用。
若攻关仍不能满足手机目标，再提交桌面本地或明确云端路径的具体影响供产品决定；
本轮没有取得缩小核心范围、上传文档、使用付费引擎或生产发布授权。

## 上传入口交互改版（2026-11-03，待验收）

本轮重新查看三家官方页面的初始界面，不上传任何用户文件。iLovePDF 的首屏用大号红色 Select WORD files 按钮，并紧接拖放提示；Smallpdf 用整块高对比度投放区包围选择入口；Adobe 用独立拖放面板、文档图形和高对比度选择按钮。共同特征是先让用户明确选文件，说明文字处于辅助位置。来源：https://www.ilovepdf.com/word_to_pdf 、https://smallpdf.com/word-to-pdf 、https://www.adobe.com/acrobat/online/word-to-pdf.html 。这些观察只代表本轮可见界面，不推断其转换引擎或未实际操作的上传行为。

现有界面的主要问题是大量说明先于选择入口；原生选择控件的可见标签没有按钮外观，而未选文件时已出现转换按钮，两步操作的主次不清。

采用分阶段的单一主操作。初始状态展示文档图形、清晰拖放区和大号红色 Choose a Word document 入口，不显示无文件可转换的按钮。选定后收起空态，显示文件名、大小、本地选择状态与次要 Change document 操作，再展示主要 Upload and convert 按钮。云端位置、明确上传时机和临时保留说明仍在转换按钮前可见；选择和拖放仍不创建任务、不上传。保留 DOCX/30 MiB/200 输出页边界、布局变化提示、支持范围、取消、下载与确认删除。

原生 input 继续覆盖可见选择目标，不使用转发点击，以保留手机文件选择器兼容性。拖放高亮不使用虚构进度；上传百分比来自真实事件，转换阶段仍使用真实状态。连接检查期间隐藏无必要的重连按钮，失败后恢复重连。

验证要求：320/390/1280px 无横向溢出；原生文件选择器可用；选定和换文件不上传；拖放可选定并正确退出高亮；离线、错误、取消、预览、下载、删除与离开确认保留；完整累计 CI 通过后交付本地预览。本次界面改版不自动替换已上线版本，先评审实际可交互界面。

本地验证：542 项单元/集成测试通过；Chromium 与 WebKit 共 22 项 Word 交互测试通过，覆盖 320/390/1280px 原生选择器与阶段主操作、拖放、转换/预览/下载/取消/删除、错误恢复和离开确认。累计独立输出校验通过：页码 21 份/374 页，解锁 33 份/361 页及 21 份/367 页两组。固定回归样本的原始提交字节已恢复；截图与生成输出仅保留在忽略研究目录。完整 GitHub CI 需以此分支精确提交核对，不沿用上一版发布结果。
